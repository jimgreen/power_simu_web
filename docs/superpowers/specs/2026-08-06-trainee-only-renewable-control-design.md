# 新能源控制仅依赖学员台的架构设计

## 背景

当前学员台新能源实时控制虽然运行在学员台 WEB 后台，但控制管理器仍然直接读取学员台保存的模拟台连接信息，拼接模拟台快照地址，并直接请求模拟台实时数据；闭环模式下，控制管理器还会直接向模拟台指令接口发送遥调命令。

这种实现把新能源控制算法与模拟台通信协议、连接地址、远端快照结构和远端指令接口绑定在一起，存在以下问题：

- 新能源控制模块同时承担控制决策和模拟台通信两种职责。
- 控制模块需要理解 `teacher_api_base`、`snapshot_path` 和 `command_path` 等模拟台连接字段。
- 浏览器页面、学员台代理接口和新能源控制后台可能分别获取实时数据，形成多份快照和重复请求。
- 模拟台连接切换、断线重连和指令转发变化会直接影响控制模块内部实现。
- 无法严格保证控制算法只使用学员台设备参数。

本次设计将模拟台通信完全收口到学员台实时交互层。新能源控制模块只与学员台交互，不知道模拟台是否存在，也不持有或访问任何模拟台地址。

## 已确认原则

1. 新能源控制模块与模拟台无关，不直接读取模拟台数据，也不直接向模拟台发送命令。
2. 新能源控制模块只读取学员台后台已经接收、合并并缓存好的实时快照。
3. 新能源控制算法只使用学员台当前模型的设备参数、量测定义、控制定义和本地控制配置。
4. 模拟台设备参数不会自动或实时同步到学员台。
5. 只有人工执行“模型初始化”时，学员台才允许更新本地模型、图形、量测和控制定义。
6. “启动接收”只建立实时数据链路，不更新学员台静态定义。
7. 闭环控制仍然可以执行，但新能源控制模块只把策略提交给学员台本地指令入口；后续是否以及如何转发由学员台实时交互层负责。
8. 后台接收、快照缓存和新能源控制不能依赖某个浏览器页面保持打开。
9. 多个学员台 WEB 页面必须读取同一个后台实时快照和同一个新能源控制实例。

## 方案选择

### 方案 A：学员台实时交换服务

在学员台后台增加统一实时交换服务，负责实时接收、快照缓存、量测增量、连接状态和指令转发。新能源控制管理器通过本地接口读取快照并提交指令。

该方案职责清楚、支持无浏览器运行、支持多页面共享，并能够通过接口注入进行独立测试，采用此方案。

### 方案 B：新能源控制访问学员台本机 HTTP 接口

控制管理器通过 `localhost` HTTP 请求学员台快照和指令接口。虽然表面上只访问学员台，但会引入端口发现、服务启动顺序、自请求重入、HTTP 超时和额外序列化，且控制模块仍然承担网络通信，不采用。

### 方案 C：浏览器向新能源控制推送快照

由学员台前端页面读取实时数据后再上传给新能源控制后台。浏览器关闭、页面切换或多个页面并存都会影响算法，不符合后台共享控制要求，不采用。

## 总体架构

```text
外部实时数据源
       |
       v
学员台实时交换服务
  - 接收工作线程
  - 连接状态管理
  - 远端运行数据缓存
  - 本地定义覆盖
  - 量测增量生成
  - 学员台指令入口
       |
       +--------------------> 学员台首页、SVG、量测和控制页面
       |
       v
新能源控制管理器
  - 读取学员台控制快照
  - 执行新能源控制算法
  - 生成策略、指标和日志
  - 向学员台指令入口提交闭环策略
```

依赖方向必须保持单向：

```text
renewable_control -> trainee_exchange -> external connection
```

禁止出现：

```text
renewable_control -> simulator URL
renewable_control -> simulator snapshot API
renewable_control -> simulator command API
```

## 组件设计

### 学员台实时交换服务

新增独立的学员台实时交换组件，建议位于 `simu/trainee_exchange.py`。它是学员台子系统的一部分，不属于新能源控制算法。

每个学员台模型维护一份独立状态：

```text
model_id
connection_signature
receive_active
latest_runtime_snapshot
latest_received_at
latest_receive_error
runtime_revision
measurement_delta_sequence
measurement_delta_history
fetch_in_progress
```

主要接口：

```python
start_receiving(model_id)
stop_receiving(model_id)
receive_status(model_id)
snapshot(model_id, options=None)
control_snapshot(model_id)
measurement_delta(model_id, after_seq)
submit_commands(model_id, payload)
invalidate_model(model_id)
close()
```

其中：

- `snapshot()` 面向学员台页面。
- `control_snapshot()` 面向新能源控制，返回控制所需的完整实时字段和数据年龄。
- `submit_commands()` 是学员台统一指令入口，人工指令和新能源自动指令均可复用。
- `invalidate_model()` 在模型初始化、模型删除或连接定义变更时清除该模型的运行缓存。

### 后台接收工作线程

“启动接收”后，学员台实时交换服务在后台持续获取动态数据。接收任务不依赖前端 `setInterval`，也不因页面关闭而停止。

后台基础快照至少包含：

- 仿真时钟及仿真时刻。
- 实时量测值和真值。
- 设备运行状态、开关状态、控制模式和 SOC。
- 设备拓扑运行状态及死岛状态。
- 当前有效控制指令和反馈。

基础接收明确使用动态快照，不下载模拟台静态定义。连接中的静态参数变化不能进入学员台缓存。

页面需要更多运行日志或历史数据时，由学员台实时交换服务负责补充获取或读取其本地缓存；新能源控制不参与页面数据获取。

每个模型设置独立的短临界区和获取互斥，避免后台线程与多个页面同时请求时对同一连接发起重复快照请求。

### 学员台运行快照缓存

交换服务只缓存外部来源的动态运行数据。读取快照时，再与学员台当前模型的本地静态定义进行合并。

本地权威字段包括：

- `model`
- `definitions`
- `settings`
- `device_parameters`
- 图形和控制定义
- 量测 `weight` 与 `valid`

动态权威字段包括：

- 量测实时值与真值
- `run_stat`
- 开关 `status`
- 实时控制模式
- 实时 SOC
- 实时设定反馈
- 仿真时钟
- 拓扑运行状态与死岛状态

因此，学员台人工修改设备参数后，无须复制或重建远端快照；下一次 `control_snapshot()` 读取时自然叠加最新本地参数。

快照发布采用“构造候选快照后一次替换”的方式，读线程不能看到只更新了一半的量测或设备状态。

### 新能源控制管理器

`TraineeRenewableControlManager` 改为依赖学员台接口，而不是依赖远端请求函数。

建议构造形式：

```python
TraineeRenewableControlManager(
    services,
    snapshot_provider=trainee_exchange.control_snapshot,
    command_sink=trainee_exchange.submit_commands,
)
```

新能源控制模块中应删除或迁出以下职责：

- 模拟台连接解析。
- URL 拼接。
- HTTP JSON 请求。
- 模拟台快照获取。
- 模拟台静态签名缓存。
- 模拟台指令接口调用。
- `teacher_api_base`、`snapshot_path`、`command_path` 等字段判断。

控制模块保留：

- 控制运行状态。
- 周期调度。
- 策略参数持久化。
- 控制计划计算。
- 数据质量校核。
- 仿真时刻去重。
- 控制指标、趋势和决策日志。
- 向学员台指令入口提交控制策略。

### 学员台指令入口

闭环模式下，新能源控制管理器把命令提交给学员台实时交换服务：

```text
新能源控制 -> 学员台指令入口 -> 学员台交互层 -> 外部执行端
```

新能源控制命令继续携带：

- `source=trainee-renewable-priority-backend`
- 自动指令有效期。
- 本机下发时刻与仿真时刻。
- 遥调点名称、设备类型、设备名称、设定类型和目标值。
- 策略指标和决策摘要。

新能源控制日志只记录“提交学员台指令入口”和“学员台返回结果”。外部执行端接受、忽略或失败等通信细节由学员台实时交换服务记录，避免控制模块出现模拟台专用文案。

人工遥控、人工遥调和自动控制可以共享同一学员台指令入口，但仍按现有人工/自动来源、覆盖优先级、有效期和人工退出规则处理。

## 数据流

### 启动接收

1. 用户完成模型初始化，学员台保存连接定义和本地静态模型。
2. 用户点击“启动接收”。
3. 学员台更新接收状态。
4. 学员台实时交换服务启动对应模型的后台接收任务。
5. 第一份动态快照完整到达后，交换服务原子发布缓存。
6. 学员台页面和新能源控制开始读取同一份缓存。

模型初始化和启动接收必须继续保持分离。启动接收不得下载或覆盖静态定义。

### 控制计算

1. 新能源控制周期到达。
2. 控制管理器调用学员台 `control_snapshot(model_id)`。
3. 交换服务读取最新动态缓存。
4. 交换服务叠加当前学员台本地定义和人工修改。
5. 交换服务返回快照、接收时间、数据年龄和接收状态。
6. 控制管理器执行现有拓扑识别、数据校核和控制策略计算。
7. 开环模式只保存策略和日志。
8. 闭环模式把命令提交给学员台 `submit_commands()`。

### 接收刷新

浏览器页面刷新只读取交换服务缓存，不承担维持新能源控制数据链路的责任。页面主动刷新可以请求交换服务加快一次接收，但不能建立第二套独立快照状态。

### 模型切换与初始化

- 模型切换只切换当前页面和控制目标，不混用不同模型缓存。
- 模型初始化完成后，交换服务清除该模型旧运行缓存和量测增量序号。
- 模型初始化后仍保持当前显示模型不变，沿用现有交互规则。
- 新模型必须重新启动接收并获得第一份实时快照后，才能启动新能源控制。

## 状态与失效处理

### 尚未启动接收

新能源控制不能启动，也不能执行单次控制计算。返回明确状态：

```text
请先启动接收。
```

### 已启动接收但首帧未到

新能源控制不能使用学员台本地仿真结果代替接收数据。返回：

```text
学员台正在等待第一份实时数据。
```

### 短时接收失败

交换服务保留最后一份完整快照，记录数据年龄和最近错误。控制算法可以继续生成开环观察策略，但是否允许闭环下发由现有数据质量门槛决定。

### 数据过期

超过允许数据年龄时：

- 禁止闭环下发。
- 保留最近一次计划和趋势。
- 运行日志明确显示数据年龄和接收错误。
- 不回退到学员台本地仿真运行值，也不由控制模块自行连接外部数据源。

### 停止接收

- 学员台实时交换服务停止对应模型的后台接收任务。
- 保留最后快照用于页面冻结展示。
- 新能源实时控制同步停止。
- 禁止单次闭环计算和下发。

### 连接切换竞态

每次获取数据前后比较连接签名。若模型初始化、连接地址或目标模型在请求期间发生变化，则丢弃候选快照，不覆盖当前缓存，也不生成控制计划或下发命令。

## 现有接口调整

以下学员台接口路径可以保持不变，以降低前端改动：

- `GET /api/trainee/snapshot`
- `GET /api/trainee/measurements/delta`
- `POST /api/trainee/commands`
- `GET/POST /api/trainee/receive-state`
- `POST /api/trainee/receive`
- `GET/POST /api/trainee/renewable-control`

但内部职责调整为：

- `/api/trainee/snapshot` 读取学员台交换服务缓存，而不是由每个页面直接代理远端快照。
- `/api/trainee/measurements/delta` 从学员台缓存变化生成增量。
- `/api/trainee/commands` 提交到学员台统一指令入口。
- `/api/trainee/receive` 启停学员台后台接收任务。
- `/api/trainee/renewable-control` 只操作新能源控制状态与策略，不触发外部快照获取。

## 持久化边界

持久化内容：

- 学员台模型定义。
- 学员台人工设备参数和量测定义修改。
- 学员台接收连接定义及启停状态。
- 新能源控制配置、循环方式和有效期。

不持久化内容：

- 实时快照缓存。
- 量测增量缓存。
- 正在进行的网络请求。

WEB 服务重启后：

1. 加载学员台模型和人工修改。
2. 加载接收状态。
3. 对处于接收状态的模型重新启动后台接收任务。
4. 在收到首帧前阻断新能源控制。

## 测试设计

### 模块隔离测试

静态检查 `simu/renewable_control.py`，确认不再包含：

- `teacher_api_base`
- `snapshot_path`
- `command_path`
- `urlopen`
- `urljoin`
- 模拟台快照获取函数
- 模拟台指令发送函数

控制管理器测试使用假的 `snapshot_provider` 和 `command_sink`，不启动 HTTP 服务，不创建模拟台对象。

### 学员台快照测试

- 后台接收任务在没有浏览器页面时持续更新缓存。
- 多个页面读取相同快照修订号和仿真时刻。
- 外部快照中的静态设备参数不会覆盖学员台参数。
- 学员台人工修改参数从下一次读取立即生效。
- 量测值来自动态缓存，量测 `valid/weight` 来自学员台定义。
- 连接切换期间返回的旧快照被丢弃。

### 新能源控制测试

- 未启动接收时控制被阻断。
- 已启动但首帧未到时控制被阻断。
- 控制只使用学员台快照提供者。
- 同一仿真时刻最多生成和提交一次自动策略。
- 开环模式不会调用学员台指令入口。
- 闭环模式只调用一次学员台指令入口。
- 指令入口失败时保留计划并记录学员台提交失败，不出现模拟台专用调用。
- 短时断线使用学员台最后快照并正确计算数据年龄。
- 数据过期时禁止闭环下发。

### 回归测试

- 模型初始化和启动接收仍保持两个独立操作。
- 学员台人工遥控、遥调继续使用统一指令入口。
- SVG、首页、量测页面和新能源曲线继续正常刷新。
- 多模型缓存、接收状态和控制状态相互隔离。
- 人工修改持久化和重置逻辑保持不变。

## 实施顺序

1. 先为学员台实时交换服务编写失败测试。
2. 实现每模型运行缓存、后台接收生命周期和本地定义覆盖。
3. 将学员台快照、量测增量和指令路由迁移到交换服务。
4. 为新能源控制管理器定义 `snapshot_provider` 与 `command_sink` 接口。
5. 编写隔离失败测试，证明当前控制模块仍直接依赖模拟台。
6. 删除新能源控制中的连接解析、远端获取、远端缓存和直接指令发送逻辑。
7. 接入学员台交换服务，并保持现有控制算法计算逻辑不变。
8. 更新状态文案、运行日志和数据源标签。
9. 执行学员台接收、人工指令、模型初始化、实时控制和多模型回归测试。

## 非目标

- 本次不修改新能源控制策略数学逻辑、步长、死区、SOC 降额或拓扑分类规则。
- 本次不修改模拟台的快照和指令协议。
- 本次不让模拟台设备参数自动同步到学员台。
- 本次不依赖浏览器 Service Worker、前端本地存储或页面常驻来维持后台接收。
- 本次不新增第二套人工指令优先级规则。

## 验收标准

1. 新能源控制模块中不存在模拟台连接字段和直接网络访问代码。
2. 新能源控制模块的所有数据输入均来自学员台 `snapshot_provider`。
3. 新能源控制模块的所有闭环输出均提交给学员台 `command_sink`。
4. 没有浏览器页面时，学员台启动接收后仍能更新快照并运行新能源控制。
5. 模拟台设备参数实时变化不能改变学员台新能源控制计算参数。
6. 学员台人工设备参数修改从下一控制周期生效。
7. 接收未启动、首帧未到和数据过期均不会产生不安全的闭环下发。
8. 多模型、多页面和 WEB 重启后的行为符合本设计。
